## Context

See proposal.md - Why. Bundles are loaded wholesale into memory already (`loadBundle` in
`src/core/bundle.ts` walks the tree and parses every concept up front) — `catalog`,
`status`, and `check` all do this on every invocation with no caching layer. `search` fits
the same shape: load the bundle, do the work, exit. There is no long-running process and no
existing persistence mechanism beyond the Markdown files themselves.

## Goals / Non-Goals

**Goals:**
- Rank results by relevance across frontmatter and body.
- Zero persisted state: nothing to go stale, nothing a `check`/`status`-style command would
  need to detect drift in.
- Stay within okfctl's existing dependency profile: pure JS/TS, no native build step, so
  `npm install` behaves the same on every platform.

**Non-Goals:**
- Sub-linear scaling to tens of thousands of concepts. OKF bundles are personal/team
  knowledge corpora, not a search-engine workload; if this ever becomes the wrong tradeoff,
  a persisted-index design is a separate proposal, not a retrofit of this one.
- Fuzzy/semantic (embedding-based) search. Lexical ranking is enough for the "which file
  already covers this" use case; semantic search is a different tool with different
  failure modes (silent false positives) that doesn't fit an unreviewed-by-default CLI.
- Query language (boolean operators, field filters like `type:Decision`). A single
  free-text query is the whole surface for this change; field filters can be a later
  addition to the same command without changing the indexing approach.

## Decisions

**Library: MiniSearch, indexed in memory per invocation.**

Alternatives considered:

- **SQLite + FTS5** (via `node:sqlite`, stable since Node 22, or `better-sqlite3`). Gives
  real ranking (BM25) and would scale far past what this tool needs, but requires a
  persisted `.db` file to be worth its own cost — indexing 2k Markdown files from scratch
  on every invocation defeats the point of using a database at all. A persisted index
  reintroduces exactly the staleness problem `okfctl status`/`check` exist to catch
  elsewhere in the bundle (see proposal.md), and `node:sqlite` is only stable on Node ≥ 22
  while this project targets Node ≥ 20.19 (package.json `engines`). Rejected.
- **Shell out to ripgrep.** Zero new dependency, always fresh, trivially correct. But no
  relevance ranking (results come back in file order, not match quality), no straightforward
  way to weight a title match above a body match, and it depends on `rg` being on the
  caller's `PATH`, which okfctl otherwise never requires. Rejected as the primary mechanism,
  but worth keeping in mind as a zero-dependency fallback if the chosen library ever becomes
  a liability.
- **FlexSearch.** Comparable pure-JS option, generally faster on very large corpora, but a
  more complex API (manual field configuration, worker/document modes) for a win that only
  matters well past this tool's expected corpus size. MiniSearch's API is a closer match to
  "index a list of objects, search, get ranked ids back" with less code to maintain.
- **MiniSearch** (chosen). Pure TS, zero native dependencies, index-per-invocation is
  designed into its API (cheap to construct, not meant to be kept warm across processes),
  built-in field boosting (needed for the "title/description ranks above body" requirement),
  and prefix/fuzzy matching out of the box.

**Indexed fields and boosting.** `title` and `description` are boosted above `body` and
`tags`, per the Query Search requirement ("a match in title or description ranks above a
match found only in body"). MiniSearch supports per-field boost natively, so this is
configuration, not custom ranking logic.

**No persisted index, ever — not even as an opt-in cache.** Once a cache file exists, some
later change will need to reason about invalidating it, and that reasoning is the same
staleness class this design explicitly avoids. If invocation-time indexing ever measures
too slow in practice, the fix is a different design (see Non-Goals), not a cache bolted
onto this one.

## Performance

Measured, not estimated. Fixtures of 3 KB concepts (frontmatter, five ~70-word paragraphs),
generated by a throwaway script; medians of five runs on this development machine.

| Concepts | `loadBundle` | Index build | Query | End-to-end `okfctl search` |
|---:|---:|---:|---:|---:|
| 1,000 | 100 ms | 93 ms | 0.08 ms | **375 ms** |
| 2,000 | 214 ms | 177 ms | 0.06 ms | **565 ms** |
| 10,000 | 1,100 ms | 916 ms | 0.07 ms | **2,237 ms** |

Query time against a built index is ~0.07 ms and flat across all three sizes, so ranking is
free; the entire cost is getting to the index. Both halves of that are linear — roughly
100 ms of bundle loading and 90 ms of indexing per 1,000 concepts — and neither dominates
the other, which corrects this document's earlier guess that `loadBundle` would. Node
startup is a further ~35 ms, and the remainder is module loading.

For calibration, `okfctl status` on the same 10,000-concept bundle takes 1,297 ms: search
is not introducing a new class of cost, it is paying the same `loadBundle` bill every read
command already pays, plus about the same again to index.

The Non-Goal of sub-linear scaling holds at the sizes this tool targets. At 1,000-2,000
concepts search returns in well under a second, which is the interactive band. At 10,000 it
is over two seconds, which is not — a bundle that large is the signal named in Risks below,
and the answer there is a different design, not a cache.

## Risks / Trade-offs

- **[Risk]** Every invocation pays full indexing cost — there is no "warm" mode. →
  **Mitigation**: acceptable at target corpus sizes (see Performance); if a bundle grows
  large enough that this becomes noticeable, that is the signal to revisit with real
  numbers, not to pre-optimize now.
- **[Risk]** MiniSearch's relevance ranking (TF-IDF-style, not BM25) is simpler than
  SQLite FTS5's. → **Mitigation**: acceptable for this tool's use case (finding the right
  file among a few dozen candidates), where "roughly right" ranking is enough; nothing in
  the spec promises exact BM25-equivalent ordering.
- **[Risk]** A new runtime dependency is a new thing to keep patched. → **Mitigation**:
  MiniSearch has no transitive runtime dependencies of its own and a small, stable API
  surface, keeping the addition low-maintenance.

## Migration Plan

None required — this is a new, additive command. No existing behavior changes, no data
migration, nothing to roll back beyond removing the command and the dependency.
